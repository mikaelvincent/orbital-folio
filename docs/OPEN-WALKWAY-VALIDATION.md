## Visual and implementation tradeoffs

Desktop rooms use the available horizontal space; phones preserve the same room order and the left passage. At narrow aspect ratios, keeping doorway controls visible prevents cropping every part of the cabin border. Peripheral docking/solar hardware may crop in the phone overview. This preserves useful navigation at the expense of showing the complete silhouette at once.

Idle interior diffuse color is scaled to 0.28, screens to 0.22 and fixture emission to 0.10, while room labels retain their color. These are material values, not measured luminance percentages. The original centralized cabin light was replaced with lights at the actual fixture positions, removing the isolated bright patch between them. Hover increases light; selection restores normal light.

Side doorways are open rounded rectangles with flat, forward-facing captions. Cross-row camera travel follows the left walkway without rotating the vessel. Hovering or focusing a doorway adds a bounded look across its threshold. Rapid retargets retain velocity and use the current route position, avoiding jumps to a presumed previous arrival. The hallway, geometry and route planner add initial implementation effort; shared model metadata keeps navigation and accessible controls aligned during future edits.

The Earth uses a generated periodic gradient volume with advected wisps and filtered detail. Texture payload remains 474,357 bytes on desktop and 81,141 on mobile including mipmaps, with no external image requests. Fine cloud structure was inspected visually; no claim is made that this resolves every temporal aliasing artifact. The CPU shader approximation has higher cross-resolution alpha error than the previous field. It is explicitly retained in `cloud-sampling-audit.json`, with the limits described in `cloud-review.md`. The richer field adds one-time generation cost; its equal texture size does not establish equal or faster GPU cost.

## Performance observations

The first current production desktop overview and Projects runs at 1440×1000, effective DPR 1, recorded approximately 49–50 ms median / 66.7 ms p95 over 360 frame intervals. These are material slow samples and remain in `browser-qa.json`. A later unchanged production overview repeat recorded 16.7 ms median / 18.6 ms p95 and zero intervals above 50 ms. A subsequent settled Projects repeat recorded 16.7 / 18.5 ms with zero intervals above 50 ms. The renderer-absent development control at the same viewport and DPR recorded 180 visible-tab callbacks in 3.010 seconds, with 16.7 / 18.6 ms median/p95 and zero canvases. The cause of this variability is unresolved; the faster run does not erase the earlier behavior or prove an optimization.

The renderer caches settled GTAO and static shadow maps, caps drawing-buffer size, and stops rendering in Reading view or hidden/reduced-motion states. Its frame-window diagnostics retain 360 intervals across navigation and therefore need enough settled active time before a route-specific reading. `renderCpuMs` excludes asynchronous GPU work and later diagnostic writes; it is not total frame time. The application includes a development-only renderer-absent/paused RAF control to help distinguish broad host scheduling problems. That control does not isolate shaders, draw calls or GPU cost.

Production rendering performance, physical touch hardware, full manual screen-reader behavior and public deployment remain separate practical limitations. The seeded local site stays available for exploration; no public domain deployment is claimed.
